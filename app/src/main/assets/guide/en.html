DVWA Offline – User Guide

1. What is DVWA?

DVWA (Damn Vulnerable Web Application) is a practice app that is vulnerable on purpose. You use it to learn how common web attacks work (SQL Injection, XSS, CSRF and more) and how good code stops them.

  • This Android edition is fully native and offline: no WebView, no internet permission, no web server. Every "attack" only touches the app's own private data.
  • Legal use only: practise here, or on systems you own or have written permission to test. Never try these payloads on real websites.
  • XSS, CSP Bypass and JavaScript Attacks are simulated natively: there is no browser engine, so the app analyses the output and shows "⚠ XSS fired" with a simulated alert dialog instead of running real JavaScript.

2. Logging in

  • Default login: admin / password
  • Other accounts: gordonb / abc123, 1337 / charley, pablo / letmein, smithy / password
  • Use Logout (menu ☰ or the ⋮ toolbar menu) to switch user. Some modules (for example Authorisation Bypass) need a non-admin user.
  • Change the app language any time: the 🌐 button on the login screen, Language in the drawer under Settings, or the ⋮ menu.

3. Setup / Reset DB

  • Open the menu ☰ → Setup / Reset DB → press Create / Reset Database.
  • This restores the 5 users and their passwords, empties the guestbook, deletes uploaded files and clears session data.
  • Use it whenever you changed a password (CSRF, CAPTCHA) and cannot log in, or when Stored XSS entries make the guestbook messy.

4. Security levels

Open ☰ → DVWA Security, pick a level and press Submit. The level badge on every module shows the current level.

  • Low – no protection at all. Best for learning the basic attack.
  • Medium – the developer tried to protect the code but made mistakes (weak filters, blacklists).
  • High – harder or unusual protections, like a CTF challenge. Some attacks need a trick.
  • Impossible – the secure version. Compare its source code with the other levels to learn the right defence.

Tip: start every module on Low, then move up one level at a time.

5. Tools on every module screen

  • View Source – shows the real DVWA PHP code for the current level. Tabs switch between Low / Medium / High / Impossible. The code itself is never translated.
  • Compare All – all four levels one after another, so you can spot what changed.
  • View Help – explains the vulnerability, the goal, and hints (spoilers in red) for each level, in your chosen language.
  • 🛠 Intercept & tamper panel (orange, tap to open) – the native replacement for Burp Suite / browser DevTools. Here you edit hidden form fields, user_token, headers (Referer, User-Agent), cookies, file names, Content-Type and client-side limits like maxlength.
  • Go to URL… bar (⋮ toolbar menu) – a simulated address bar. Type a DVWA path such as /vulnerabilities/authbypass/ or /vulnerabilities/sqli/ to open that page directly.
  • Brute Force wordlist runner – in the Brute Force module, the "Attack helper" card tries every password in your list (one per line) against the login, like Burp Intruder, and stops at the first success.

6. Module walkthroughs

Brute Force

  • Try: username admin, then run the Attack helper with a short wordlist.
  • Example: wordlist containing 123456, letmein, password.
  • Success: "Welcome to the password protected area admin" with the user's avatar.
  • Impossible defends with a CSRF token, a random delay and an account lock after 3 failed logins.

Command Injection

  • Try: chain a second command after the IP address.
  • Examples: 127.0.0.1; cat /etc/passwd (Low), 127.0.0.1 | whoami (Medium/High).
  • Success: the output shows the command result (from a simulated Debian shell; nothing runs on your phone).
  • Impossible defends by accepting only four numeric parts of an IP address.

CSRF

  • Try: use the "Attacker: forged link" card so the logged-in victim opens a URL that changes the password.
  • Example: http://127.0.0.1/vulnerabilities/csrf/?password_new=hacked&password_conf=hacked&Change=Change
  • Success: "⚠ CSRF succeeded — the victim's password was changed". Log in again with the new password or reset the DB.
  • Impossible defends with an anti-CSRF token plus the current password.

File Inclusion

  • Try: change the ?page= value to read other files.
  • Examples: ../../../../../etc/passwd (Low), ....//....//....//etc/passwd (Medium), file:///etc/passwd (High).
  • Success: the file content appears, e.g. the hidden quotes from ../../hackable/flags/fi.php.
  • Impossible defends with a fixed allow-list of file names.

File Upload

  • Try: upload a PHP webshell instead of an image, then request it.
  • Example: file body <?php system($_GET['cmd']); ?> saved as shell.php, then request /hackable/uploads/shell.php?cmd=id.
  • Success: "⚠ Server executed shell.php as PHP". On Medium change Content-Type to image/png in the tamper panel; on High add the GIF89a magic bytes and use File Inclusion.
  • Impossible defends by checking extension, type and real image content, then re-encoding and renaming the file.

Insecure CAPTCHA

  • Try: skip the CAPTCHA step by editing the hidden fields in the tamper panel.
  • Example: on Low set step to 2; on Medium also set passed_captcha to true; on High use User-Agent reCAPTCHA and response hidd3n_valu3.
  • Success: "Password Changed." without solving the CAPTCHA.
  • Impossible defends by checking the CAPTCHA, a token and the current password in one request.

SQL Injection

  • Try: break out of the SQL query to read other rows and tables.
  • Examples: 1' OR '1'='1 and 1' UNION SELECT user, password FROM users# (Low); 1 UNION SELECT user, password FROM users in the tamper override (Medium).
  • Success: all users and their password hashes are listed.
  • Impossible defends with prepared statements (parameterised queries).

SQL Injection (Blind)

  • Try: ask true/false questions, because the page only says "exists" or "MISSING".
  • Examples: 1' AND 1=1# (exists) vs 1' AND 1=2# (missing); time-based 1' AND sleep(3)#.
  • Success: you can tell true from false by the message or by the response time shown.
  • Impossible defends with prepared statements and a numeric check.

Weak Session IDs

  • Try: press Generate several times and look at the dvwaSession values.
  • Example: Low counts 1, 2, 3…; Medium is the current time; High is md5 of a counter.
  • Success: you can predict the next session ID.
  • Impossible defends with a random, hashed value and Secure/HttpOnly cookie flags.

XSS (DOM)

  • Try: edit the address bar URL after default=.
  • Examples: ?default=<script>alert(1)</script> (Low); ?default=</option></select><img src=x onerror=alert(1)> (Medium); ?default=English#<script>alert(1)</script> (High).
  • Success: "⚠ XSS fired" and a simulated alert dialog.
  • Impossible defends by not decoding the input, so it is never parsed as HTML.

XSS (Reflected)

  • Try: put HTML/JavaScript in the name field.
  • Examples: <script>alert(document.cookie)</script> (Low); <SCRIPT>alert(1)</SCRIPT> (Medium); <img src=x onerror=alert(1)> (High).
  • Success: "⚠ XSS fired" with your alert text.
  • Impossible defends with htmlspecialchars() output encoding and a token.

XSS (Stored)

  • Try: sign the guestbook with a payload so every visitor runs it.
  • Examples: message <script>alert(1)</script> (Low); name <svg onload=alert(1)> after ticking "Remove client-side maxlength" (Medium/High).
  • Success: the guestbook verdict shows "⚠ XSS fired". Use Clear Guestbook or Reset DB to clean up.
  • Impossible defends by encoding both fields and using a prepared statement.

CSP Bypass

  • Try: load a script from a source the Content Security Policy wrongly allows.
  • Examples: Low: include https://pastebin.com/raw/… with simulated content alert(1); Medium: <script nonce="TmV2ZXIgZ29pbmcgdG8gZ2l2ZSB5b3UgdXA=">alert(1)</script>; High: change the JSONP callback, e.g. source/jsonp.php?callback=alert(document.cookie)//.
  • Success: "⚠ CSP allowed the script — it executes (simulated)". Nothing is downloaded.
  • Impossible defends with a hard-coded callback.

JavaScript Attacks

  • Try: submit the word success with a valid token.
  • Example: type success, open the tamper panel and press the console helper (e.g. generate_token()) so the hidden token matches, then Submit.
  • Success: "Well done!".
  • Impossible: there is no real defence – anything on the client can be changed. That is the lesson.

Authorisation Bypass

  • Try: log in as gordonb / abc123 and still use the admin-only user manager.
  • Example: Low: open the page from the menu or Go to URL /vulnerabilities/authbypass/; Medium/High: use the API console to POST {"id":2,"first_name":"Hacked","surname":"ByGordon"}.
  • Success: "User updated" even though you are not admin.
  • Impossible defends by checking the user's role on every API call.

Open HTTP Redirect

  • Try: change the redirect= value so a trusted link sends the victim elsewhere.
  • Examples: ?redirect=https://example.com (Low); ?redirect=//example.com (Medium); ?redirect=https://example.com/?a=info.php (High).
  • Success: "⚠ Open redirect…" – the target is shown, never opened.
  • Impossible defends by mapping numeric IDs to fixed pages.

Cryptography Problems

  • Low: the "secret" is XOR + Base64. Decode the intercepted message and log in with the password inside it.
  • Medium: the session token uses AES-ECB. Swap 16-byte (32 hex) blocks between tokens to build a valid admin token for Sweep.
  • High: a padding-oracle attack on AES-CBC: tamper the token/IV and watch the error messages.
  • Impossible defends with AES-GCM (authenticated encryption), so any change is rejected.

7. Troubleshooting

  • Cannot log in after a CSRF/CAPTCHA test: the password was changed. Use the new password, or reinstall – or log in as another user and run Setup / Reset DB.
  • Strange data or errors in a module: run ☰ → Setup / Reset DB.
  • Nothing happens on an XSS payload: check the level (higher levels filter more) and read View Help. Remember the effect is simulated.
  • Wrong language: change it from the 🌐 Language option. On Android 13+ you can also use Settings → Apps → DVWA Offline → Language.
  • App still broken: uninstall and reinstall the APK – all data is stored only inside the app.
  • Tutorial again: ☰ → Tutorial (first-run slides).
